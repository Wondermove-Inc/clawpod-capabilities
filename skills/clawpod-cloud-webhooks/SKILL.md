# ClawPod Cloud Webhooks

Use the paired `clawpod-cloud-webhooks` Harness for deterministic execution. Do not call the portal directly when the Harness covers the operation.

Immediately after installation, before waiting for the user to invoke the capability, deliver the post-install onboarding handoff. State that installation succeeded but connection has not started, identify the required ClawPod Cloud TA account or Webhook Manager permission, explain the approval-gated login sequence, distinguish the user's sign-in/MFA actions from the agent's automated checks, explain protected credential/session handling and revocation, and ask whether to start onboarding now. Proactively ask for the ClawPod Cloud base URL and the authorized account identifier/prerequisite. The URL, email, and claimed permission are chat-safe, but never ask for or accept a plaintext password/token in chat. Search existing secret pointers first; if none exists, request password/token through protected secret input/storage. Never ask the user to configure environment variables or run commands. Do not log in or create credential state until the user explicitly approves. Omitting this handoff is an incomplete installation.

1. Start with `system.version` and `auth.contract`. Installation is not connection. Collect the HTTPS base URL and non-secret account information, search/store protected credential pointers, and confirm the account prerequisite. TLS verification is strict by default. For an internal CA, prefer a readable PEM passed per command as `caCertPath`/`--ca-cert`; it is never copied or persisted. Use insecure TLS only on an explicitly approved internal network, pass both `insecureSkipTlsVerify`/`--insecure-skip-tls-verify` and the separate `insecureTlsRiskAccepted`/`--i-understand-insecure-tls-risk` affirmation, and never combine it with a custom CA. HTTP is always rejected. Before login, account access, cookie creation, secret injection, insecure TLS, or any mutation, obtain the corresponding explicit approval.
2. After approval, run deterministic `auth.onboard` yourself through the protected `exec.useSecrets` lane, injecting the email and password pointers as `CLAWPOD_CLOUD_EMAIL` and `CLAWPOD_CLOUD_PASSWORD`. Current Gateway `harness.run` accepts only command input and an approval intent hash, not memory-secret injection. Do not claim that lane can authenticate and do not expose secret values in argv. `auth.onboard` validates the base URL by fetching the RSA key, logs in, and supports both legacy `tenants` identity data and the current `activeTenantId`/`role`/`tenantRole`/`policyActions` contract. It keeps multiple legacy tenants blocked unless one is explicit, selects a sole legacy tenant before the current active context, verifies permission, and stops before mutation.
3. After approved login, require identity, selected tenant, and Webhooks permission readback before declaring the capability connected. Accept tenant-admin identity roles or current policy actions only when both Webhooks management and read capabilities are present; otherwise retain the separate legacy permissions endpoint fallback. Because sessions are process-memory-only, use the same protected `exec.useSecrets` lane for every later authenticated one-shot command; never ask the user to reinject credentials manually. Then inspect presets, Sources, Playbooks, Rules, and recent Events. Always bind the tenant explicitly and preflight every target against it.
4. Use Source Playbooks only for provider-common interpretation and safety constraints. Use Rule Playbooks for event-specific workflow, evidence, and escalation. Warn when Source and Rule reference the same Playbook because delivery duplicates it.
5. Reject `in`, `not_in`, `gt`, `lt`, `gte`, `lte`, and non-empty `message_template`. Block agent targets unless destination-side evidence is required and available.
6. For every mutation, run `mutation.preview`, show the redacted intended diff and effect digest, obtain approval, then execute with the same digest and a stable idempotency key. TLS exception approval never authorizes a mutation; preview and execution approvals remain separate. Never infer approval from design or preview approval.
7. For Source updates, preserve the full mutable object from a fresh GET, PUT it, and verify a fresh GET. Stop on mismatch or partial failure. Never blindly retry a mutation.
8. Reject inbound test bodies over 1,048,576 bytes. Require a sender-stable request ID. A `received=true` response without `event_id` is not acceptance.
9. Verify Event status asynchronously. Treat any non-empty `error_message` as failure even when status says `delivered`. Require destination-side evidence when delivery matters.
10. Use `event.inspect-redacted`; never return raw cookies, authorization, signatures, URL tokens, signing secrets, or sensitive headers.
11. For rotate/regenerate, warn that prior credentials may remain valid, read back `previous_secret_expires_at`, and report overlap. Never print returned secret material.

Completion requires source-of-truth readback, redacted evidence, and explicit residual limitations. Current known limits are unproven agent delivery, broken comparison/set operators, ignored message templates, silent ingress drops above 1 MiB or for unknown/disabled Sources, throttled Events remaining `accepted`, and no concurrency FIFO guarantee.
